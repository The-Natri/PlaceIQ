# Viva Cheat Sheet

One line per row, short enough to say out loud in one breath. Skim this right
before you walk in.

| Feature | Where in code | DBMS concept it proves | Why I built it this way |
|---|---|---|---|
| `placement_status` auto-updates on offer insert | `db/schema.sql` §3, `trg_offer_after_insert` | Row-level AFTER INSERT trigger | So a student's placement status can never drift out of sync with reality — it's set by the database itself the instant an offer exists, not by whichever app code happened to remember to update it. |
| `fn_check_eligibility(student_id, drive_id)` | `db/schema.sql` §4 | Stored function, single source of truth for business logic | Eligibility has to mean the same thing everywhere it's checked, so I put the rule in the database once instead of reimplementing it in Python and risking the two falling out of sync. |
| `fn_get_eligible_drives(student_id)` | `db/schema.sql` §4 | Stored function returning a set, reused by the backend | Lets the backend get a student's whole eligible-drives list in one query instead of looping `fn_check_eligibility()` per drive in application code. |
| `placed_students_view`, `company_wise_stats_view`, `department_stats_view` | `db/schema.sql` §5 | Views for abstraction and reuse | Every analytics/dashboard query that needs these joins hits the view instead of re-deriving the same multi-table join in every route file. |
| Offer accept/decline transaction | `backend/services/offer_service.py` | Explicit multi-statement transaction with commit/rollback (ACID) | The spec wanted a *visible* transaction, not one hidden behind an ORM's autocommit, so I wrote raw psycopg2 with an explicit `try / conn.commit() / except / conn.rollback()` block updating Offer, Student, and Offer_History together. |
| 5 indexes on `dept_id`, `cgpa`, `application.status`, `application.drive_id`, `drive.company_id` | `db/schema.sql` §2 | Query optimization on high-traffic filter columns | Each one maps to a specific hot-path query (eligibility checks, admin filtering by drive/status) — I indexed what's actually queried, not everything "just in case." |
| `Application` junction table | `db/schema.sql` §1 | Relational resolution of an M:N relationship | A student applies to many drives and a drive gets many applicants, so the relationship needed its own table with its own attributes (`status`, `applied_at`) rather than trying to force it into either side. |
| Normalization (3NF) | `docs/normalization.md` | Elimination of transitive/partial functional dependencies | Split out `department` and `company` as their own tables so facts like `dept_name` and `industry_sector` live in exactly one row each, instead of being copied onto every student/drive row and risking update anomalies. |
| Raw psycopg2, no ORM | `backend/db.py` | Deliberate SQL visibility over convenience | An ORM would auto-generate the queries — the whole point of this project is the SQL itself, so every query needed to be plain, visible, and something I can point at and explain, not hidden behind an abstraction layer. |
| Application deadline + PL008 | `db/schema.sql`: `drive.application_deadline` CHECK, `trg_fn_application_guard` | CHECK for a same-row rule, trigger for a cross-table rule | "Deadline before drive date" is one row, so a CHECK. "Applied before the deadline" needs the drive's row and the clock, so a trigger. The database time zone is Asia/Kolkata so a deadline means the college's end of day. Evidence: `docs/evidence/date-integrity.md`, 10 rules, 0 violations. |
| One origin, one port | `backend/app.py` (spa), `backend/serve.py` (waitress), `docker-compose.yml` | Deployment: the API and the built UI from one server | No CORS needed; the database and ML service aren't exposed (only 127.0.0.1:8080 is published). waitress, because Flask's dev server isn't for production. |
| Public sharing | `scripts/share.ps1`, `backend/utils/rate_limit.py`, `docker/set_passwords.py` | Security on a public link | Private secrets from a git-ignored file, demo passwords replaced, login rate limit (10 per 5 min per visitor). |
| Rule triggers PL001–PL008 (not eligible, drive closed, second accepted offer, offer without Selected, illegal status move, applied after the deadline) | `db/schema.sql` §6 | BEFORE triggers that RAISE an error with a custom SQLSTATE | A rule in the database holds no matter who writes: the API, psql, or a future app. The backend just maps each code to an HTTP status (`backend/utils/db_errors.py`). Evidence: `docs/evidence/triggers.md`. |
| Status state machine (Applied → Shortlisted → Interview_Scheduled → Selected → Offer_Made; Rejected/Offer_Made are final) | `db/schema.sql` `trg_fn_application_status_transition` (line 595) | BEFORE UPDATE trigger comparing `OLD` and `NEW` | A CHECK constraint sees only the new value. The transition rule needs the old one too, which only a row trigger has. |
| Application status audit log | `db/schema.sql` §7, `application_status_history` + `trg_application_status_audit` (line 655) | AFTER UPDATE trigger with `WHEN (OLD.status IS DISTINCT FROM NEW.status)` | The history is written by the database, so no code path can change a status without leaving a record. AFTER, because it should log only changes that actually happened. |
| `sp_close_drive(drive_id, INOUT rejected_count)` | `db/schema.sql` §8, line 682 | Stored PROCEDURE with its own transaction logic, called with `CALL` | Closing a drive is two writes (reject pending applicants, mark the drive Completed) that must happen together. One procedure call makes it a single unit the API can't half-do. |
| Window-function views (`RANK`, `DENSE_RANK`, `PERCENT_RANK`, `LAG`, running `SUM OVER`) | `db/schema.sql` §9, lines 716–790 | Analytic functions over partitions, with no GROUP BY collapse | "Top 3 offers per department" and "running total by month" need each row *and* its position in a group. Window functions do that in one query. The timeline view generates every month so `LAG` compares real consecutive months. |
| `mv_company_dept_placements` | `db/schema.sql` §10, line 805; refreshed by `POST /api/analytics/refresh-matrix` | Materialized view, `REFRESH ... CONCURRENTLY` with a UNIQUE index | A stored snapshot of an expensive aggregate. It shows the trade-off between staleness and speed, and the UI prints `refreshed_at` so nobody mistakes it for live data. |
| Index benchmark | `db/demos/index_benchmark.py`, results in `docs/evidence/index-benchmark.md` | `EXPLAIN ANALYZE`: Seq Scan vs Bitmap Index Scan | Measured, not assumed: on 250k applications `idx_application_drive` is about 80x faster. `idx_drive_company` barely helps, and I say so. |
| Oracle port | `db/schema_oracle.sql`, transcript `docs/evidence/sqlplus-transcript.txt` | Same design in PL/SQL: sequences + triggers, `RAISE_APPLICATION_ERROR`, a COMPOUND trigger | The lab uses Oracle. The COMPOUND trigger avoids ORA-04091 (mutating table) when the second-offer rule has to read `offer` while it is being updated. |
| Placement-probability model | `ml-service/train.py`, results in `docs/evidence/ml-results.md` | Features computed with SQL (skill count via a join), served over HTTP | Logistic regression is small and explainable (the coefficients make sense). It is honest about its limits: 36 test students, synthetic data, ROC-AUC 0.774. |

## Backup one-liners (if asked to go deeper)

- **Why is `placement_status` on `student` even though it's derivable from `offer`?** Deliberate, documented denormalization — required by the trigger, and it saves a 4-table join on the dashboard's most common read. See `docs/normalization.md`.
- **Why does declining an offer sometimes flip `placement_status` back to `'Not Placed'`?** The trigger only ever turns it ON (on offer insert); `offer_service.decline_offer()` is what turns it back OFF, but only if the student has no other Pending/Accepted offer — a check-then-act that has to happen inside the same transaction.
- **Why custom SQLSTATE codes (PL001–PL008) instead of generic errors?** The backend can tell "not eligible" (403) from "drive closed" (409) by code, not by parsing message text, which would break the moment a message was reworded.
- **What happens if two requests accept two offers for the same student at the same moment?** The PL003 trigger locks the student's row (`SELECT ... FOR UPDATE`) before counting Accepted offers, so the second request waits, then sees the first one's acceptance and is refused.
- **Isn't the materialized view redundant data?** Yes, on purpose: it is a read-only cache, rebuildable at any time from the base tables, and never written to directly. See the end of `docs/normalization.md`.
- **Why does the seed backdate the audit rows?** It replays months of history in seconds; the audit trigger stamps real time, so the seed sets each replayed row to its simulated moment. Only the seed does this.
- **What's the weakest part of the project?** The data is synthetic and CGPA is self-reported at signup. The ML numbers come from 36 test students, so they show the pipeline works, not that it would predict real placements.
- **Why junction tables for `student_skill` and `drive_eligible_dept` too?** Same M:N reasoning as `Application` — a comma-separated column would violate 1NF and make `COUNT(*)`-style queries (skill count for the ML model, eligible-department lookups) unreliable string parsing instead of real SQL.
- **Why generate the dataset instead of using real placement data?** No real student data exists for this course, and the ML model needs a *correlated* dataset, not a random one — `db/seed.py` deliberately makes CGPA/backlogs predictive of outcome so the model has real signal (see the big comment at the top of that file).
